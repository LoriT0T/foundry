# Foundry V1

The second built version of Foundry — a clean superset of V0. Everything in this folder is real and in use. V1 adds exactly one dimension: the universal discipline of operating as an agent under **external, dynamic, project-specific regulation** — while carrying no actual rules, only the method for handling being regulated. A regulated agent is not merely *aware* of its rules; it is *driven* by them — its shape, interfaces, and technology choices made *by* the regulation, not chosen for convenience and then gated.

- **`BOOTSTRAP.md`** — the birth sequence + loading rule a fresh agent runs first. V1 adds one **mandatory birth question** — *"is this project regulated?"* — answered by a recognition check that routes a *yes* to the regulatory-architecture capability (and its research playbook) before building. A positive answer also commits the build to be *driven* by the discovered rules at the architecture step, not only gated by them.
- **`foundation/`** — the *behavioral* branch: how an agent thinks and works. Loaded in full by every agent, always. (9 files: the execution loop, memory architecture, self-improvement, orchestration, reliability, the quality rubric, the red lines — now including a regulation red line — and two enforced build laws: compartmentalization and the mistake engine.)
- **`knowledge/`** — the *technical* branch: production capabilities. The index (`knowledge/INDEX.md`) is read at startup; individual capability files load **only when a task triggers them**. Spine: `INDEX.md`, `DECISION_RULE.md`, `tool-registry.md`, `INSTANTIATION_GUIDE.md`, `BOOTSTRAP_loading_section.md`. Capabilities: retrieval, guardrails, evaluation, observability, orchestration, deployment, the tool layer (MCP), memory systems, cost/routing, context engineering, and **regulatory architecture** (new in V1).

**What V1 adds over V0:** the `regulatory-architecture` capability — recognition (§1), the recurring constraint categories framed as *questions* (§2, never answers), a research-at-instantiation playbook (§3), the compliance-seam attachment pattern (§4), and **regulation drives the build** (§5) — the dimension that makes the discovered rules a *primary design input* rather than a review applied afterward. §5 carries build-shaping questions about *properties* (where data/processing may reside; what the system must connect to/defer to; how things must be stored/secured/proven/retained/destroyed; what must be recorded/reversible/auditable/human-gated), an *honesty trichotomy* (built-and-verified vs correctly-shaped-but-not-yet-connected vs deliberately-deferred — never let the first absorb the others), and a *production roadmap* requirement. Backed by an extended regulation red line in `foundation/RED_LINES.md` and the mandatory recognition question in the birth sequence. It carries **no regulation, no named regime, no sample rule, no technology, no jurisdiction** — those are the most project-specific thing there is, and the foundation stays bias-free. Loading is on-trigger: an agent in a non-regulated domain never loads the capability and behaves exactly as a V0-born agent.

**Where to start:** read `BOOTSTRAP.md`, then `knowledge/INDEX.md`. The two non-negotiable principles — *no bias* and *no authority over judgment* — are explained in the top-level README and on the site.
