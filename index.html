The idea

Two principles and a birth sequence

Foundry is two branches of documents an agent reads, plus a discipline for becoming itself. What makes it work is not the documents — it is two rules they never break, and one sequence every agent runs before it writes any code.

1 No bias

The foundation carries zero project specifics — no domain, subject, person, or goal. Everything in it is universally true. Specifics enter only at instantiation, from the agent's own context, and flow outward into that agent — never back into the foundation.

The test for anything in the branches: would this be equally true for an agent doing something completely different? If not, it doesn't belong.

2 No authority over judgment

Every file is reference material an agent builds from — never an instruction it must obey. A file's completeness is not authority: the agent always decides whether to adapt a pattern, instantiate it, or build its own.

Knowledge informs. It never commands.

The birth sequence

An agent born from Foundry decides the hard questions before any code. The answers form a reviewable birth certificate — you can read exactly what the agent decided it is before it does anything.

  1. The goal — stated in one sentence, with a concrete definition of what "working well" looks like.
  2. Judgment vs. determinism — where the work needs real judgment (reserve the model there) versus where it is rules and math (make that deterministic and reliable).
  3. The data sources — each distinct body of data the agent will work with, named.
  4. The irreversible & risky — anything that moves money, posts publicly, or deletes — gated behind a human or a hard limit.
  5. The cadence — how often it runs, and how it reports back.
After the certificate: the agent loads the behavioral foundation in full, reads the technical index, and instantiates each capability it actually needs against its own context — loading the heavy material only when a task calls for it.

Built · real · in use

Foundry V0 — the foundation that exists today

V0 is real and in use. It is organized as two branches with deliberately different loading rules — the whole reason they are kept separate.

foundation/ — behavioral

How an agent thinks and works. Small, universal, and loaded in full, every run. The execution loop, memory architecture, self-improvement, reliability, the red lines — plus two enforced build laws: compartmentalization, and a mistake-generalization engine that turns a single mistake into a rule its whole class can never repeat.

knowledge/ — technical

How an agent builds real systems. Larger, per-task, and loaded only when a task triggers it — the index is read at startup; the capability files are not. Ten production capabilities, each documenting the current standard.

The loading discipline

Load all of foundation/, always — it is bounded and universal, so the cost is fixed and small. Read only the knowledge/ index at startup, and pull a capability file only when the task in front of you triggers it. The technical branch is open-ended; loading it wholesale would flood the context for no benefit. That asymmetry is why the two branches are separate, with separate rules.

It corrects itself under real use

The first real agent built on Foundry surfaced a genuine contradiction inside Foundry itself: one reference file instructed a write that a foundation red line forbids. Because the method treats a red line as overriding any reference file, the agent resolved it correctly in the moment — and the fix was then made permanent at the class level: every place the same pattern appeared was corrected, not just the one that surfaced. A methodology built to catch and repair its own flaws under real use did exactly that on first contact with reality.
